# Upstash Redis

The shared cache and the rate-limit store.

---

## Why REST, not `redis://`

The Cloudflare Workers runtime has **no raw TCP sockets**. `ioredis`, `node-redis`
and every other wire-protocol client cannot open a connection from the edge at
all. Upstash speaks HTTP, which is the only shape that works in every place this
code runs: a local `next dev`, a CI job, and an isolate in Sydney.

This is not a preference. It is the constraint that chose the vendor.

---

## Setup

1. Create a database at [console.upstash.com](https://console.upstash.com).
2. **Region: the same one as Neon.** Cache reads sit on the request path, and a
   cross-continent round trip to save a database query is not a saving.
3. **Eviction: `allkeys-lru`.** Without it a full database starts refusing
   writes, which turns a cache into an outage. With it, the least useful keys
   are dropped and everything keeps working.
4. Copy the **REST** URL and token — not the Redis URL.

```bash
UPSTASH_REDIS_REST_URL=https://xxx.upstash.io
UPSTASH_REDIS_REST_TOKEN=AX...
```

Separate databases for staging and production. A shared one means a staging
`invalidate` clears production's cache, and a staging load test consumes
production's request budget.

## What it stores

| Purpose        | Key prefix               | TTL           | Module                                                        |
| -------------- | ------------------------ | ------------- | ------------------------------------------------------------- |
| Search results | `search:`                | 60s           | [`cache/store.ts`](../src/lib/cache/store.ts)                 |
| Facet counts   | `facets:`                | 60s           | "                                                             |
| Product cards  | `product:card:`          | 300s, tagged  | "                                                             |
| Settings       | `settings:all`           | 300s          | "                                                             |
| Marketing tags | `marketing:integrations` | 300s          | "                                                             |
| Merchant feed  | `feed:merchant`          | 3600s         | "                                                             |
| Rate limits    | `rl:`                    | window length | [`security/rate-limit.ts`](../src/lib/security/rate-limit.ts) |
| Tag membership | `tag:`                   | 4× entry TTL  | [`cache/store.ts`](../src/lib/cache/store.ts)                 |

The canonical TTLs live in the `TTL` constant so the numbers are in one place
rather than thirty.

### Choosing a TTL

- **Derived and cheap to recompute** (facets, search) → 60s. A stale facet count
  is invisible to a customer.
- **Invalidated by name on write** (product cards) → 300s. The TTL is only a
  backstop against a missed invalidation.
- **Edited by hand, read constantly** (settings, marketing tags) → 300s. A
  merchant flipping a pixel on should see it within a coffee.
- **Regenerated by a job, consumed by a crawler** (feeds) → 3600s. Nobody is
  waiting.
- **Anything correctness-critical** → not cached. Stock levels, prices at
  checkout, and order state all come from Postgres, every time.

## Rate limiting

`@upstash/ratelimit` with a **sliding window**, evaluated in a Lua script so the
read-modify-write cannot race.

Sliding rather than fixed, because a fixed window lets a caller send `2 × limit`
across a boundary — the full allowance at 11:59:59 and again at 12:00:00.

| Bucket              | Limit | Window |
| ------------------- | ----- | ------ |
| Default (per route) | 60    | 60s    |
| `auth:signin`       | 10    | 5 min  |
| `auth:register`     | 5     | 1 hour |
| `auth:forgot`       | 5     | 1 hour |
| `checkout`          | 20    | 5 min  |
| `klarna-push`       | 300   | 60s    |

Denials are cached in process memory for the rest of the window: once a caller
is over the limit, asking Upstash again on every request pays network latency to
learn something already known — and under an actual flood that is when the extra
requests hurt most.

### Fail-open, loudly

If Upstash is unreachable, `rateLimit` **allows** the request and logs an error.

Both options are bad. Rejecting everything turns an Upstash blip into a full site
outage; allowing everything removes the limit until it recovers. Allowing is the
lesser harm because Cloudflare's WAF is still in front of this, and the error log
is what makes it a known degradation rather than an invisible one.

`/api/health/deep` reports `cache.ok: false` in that state, and it is worth an
alert.

### Identity

`clientIdentifier` prefers `CF-Connecting-IP`, which Cloudflare sets from the TCP
peer and a client cannot forge. `x-forwarded-for` is a header anyone can send;
reading it when `CF-Connecting-IP` exists is how limiters get bypassed with one
extra header. When it is used, only the **first** entry is trusted — the last is
whatever the client appended.

## The in-process fallback

With Upstash unconfigured, both the cache and the limiter fall back to process
memory, log once, and are reported by `productionReadiness()`.

The fallback exists so a fresh clone runs. **It is not a deployment target.** On
Workers each isolate keeps its own counter, so "60 requests a minute" becomes "60
per isolate per minute", which is not a limit at all.

## Invalidation

```ts
import { invalidate, set, keys, TTL } from '@/lib/cache/store';

await set(keys.productCard(id), card, TTL.productCard, ['products', `product:${id}`]);
await invalidate(`product:${id}`); // one product
await invalidate('products'); // every product card
```

Tag membership is a Redis set per tag, so invalidation is one lookup rather than
a `SCAN` across the whole keyspace. The tag sets carry a TTL of their own — a
generous multiple of the entry's — because without one they accumulate dead key
names forever, and eventually a single `invalidate` deletes ten thousand keys
that expired last month.

Writes go through a pipeline: every command is its own HTTP request, and a
product page writing four tagged keys would otherwise pay four round trips.

### This is not Next's cache

Two separate layers, and confusing them wastes an afternoon:

|             | `lib/cache/store.ts` (Upstash) | `unstable_cache` / `revalidateTag`          |
| ----------- | ------------------------------ | ------------------------------------------- |
| Stores      | Arbitrary values               | Rendered page and route output              |
| Backed by   | Upstash                        | R2 + KV + Durable Objects                   |
| Cleared by  | `invalidate(tag)`              | `revalidateTag(tag)`                        |
| Third layer | —                              | Cloudflare's edge cache, purged via the API |

`revalidateTag` does not clear Upstash. `invalidate` does not clear the edge.

## Monitoring

In the Upstash console: **commands per second**, **latency** (p99 under 50ms
in-region), **bandwidth**, and **daily request count** against the plan limit.

A sudden rise in commands usually means a cache key gained accidental
cardinality — a key built from a full query string rather than a normalised
fingerprint is the classic version. Every entry is then a miss, and the cache
becomes pure overhead.

---

## Cost

Billed per request. Two things keep it down:

1. **Pipelining.** Four commands in one HTTP request is billed as four commands
   but costs one round trip.
2. **The ephemeral denial cache.** Under an attack, most limit checks are
   answered from memory rather than from Upstash — which is exactly when the
   request count would otherwise spike.

If costs rise unexpectedly, look for a low-TTL key with high cardinality before
looking at traffic.
